## 🗂️ `GlobCachePlugin` now short-circuits matched requests

- 🚦 **Matched files no longer fall through the plugin chain** — when a request matches the configured glob patterns, `GlobCachePlugin` now sets `continueCheck = false` and `needValidation = false` together with `customResponse`, so the cached (or freshly fetched) response is returned immediately.
- 🐛 **Fix** — previously the plugin only assigned `customResponse` and let the remaining plugins and the Router run, which could overwrite the response or serve an error page for a file that was already cached.

---

## ⚠️ Breaking Changes

> [!WARNING]
> **The engine now evaluates `customResponse` before `continueCheck`.**
>
> Previously, `continueCheck = false` aborted the pipeline immediately and sent the request to the network, silently discarding any `customResponse` set by a plugin. Now the order is:
>
> 1. `customResponse` is a `Response` → returned immediately (even if `continueCheck` is `false`).
> 2. `continueCheck === false` → request goes straight to the network.
> 3. Otherwise → the Router logic runs as usual.
>
> **Action required:** if you were relying on `continueCheck = false` to *discard* a `customResponse` and force a network request, remove the `customResponse` assignment — the flag no longer overrides it. Custom plugins that set both properties will now return the response instead of hitting the network.

```js
// ⚠️ Before: the response was ignored and the request went to the network.
result.customResponse = new Response('cached');
result.continueCheck = false;

// ✅ Now: the response above is returned. To keep the old behavior,
// do not assign `customResponse`.
result.continueCheck = false;
```
